# note画像配置と編集失敗からの復旧

## 素材と本文の対応

- 編集前に対象下書き、本文、見出し、画像数、画像マーカー、重複段落を読み取る。共有リンクのアクセスキーをスキルやログ例へ保存しない。
- 各素材を「実スクショ」「説明イラスト」「公式支給素材」に分類し、配置先の前後の文章を指定する。説明用の生成UIを公式操作画面や実験証拠と呼ばない。
- 失敗例の巨大印影など、本文が説明する欠陥は勝手に正常化しない。修正対象と意図的な失敗表現を区別する。
- 実スクショが見つからなければ不足を報告する。再生成画像で代用しない。ファイル名の存在だけで実験内容を確認済みにしない。

## 成功した画像挿入手順

2026年9月のセッションで、本文を一括貼り替える方式ではなく、次の標準UI操作による画像1枚の挿入と下書き保存を確認した。ラベル、パス、キーは実行環境で再確認する。

1. 現在のブラウザ操作スキルを読み、対象の編集タブを再利用する。同じ下書きの編集タブを増やさない。
2. 配置先の段落をクリックする。別の読み取り操作で `document.activeElement` が本文の編集可能要素であることと、`window.getSelection()` の文字列・オフセットが目的段落にあることを確認する。
3. noteの「メニューを開く」から「画像」を選ぶ。展開後のDOMを確認する。Homeキーで段落先頭へ移動したと推測して貼り付けない。
4. ファイル選択イベントの待受をクリック前に登録し、標準ファイル選択で画像1枚をアップロードする。ブラウザへのファイル共有方法は現在のブラウザ手順に従う。
5. 「画像がアップロードされました」はアップロード成功のみを意味する。画像要素、その前後の段落、見た目、本文の保持、見出し数を読み取って配置を確認する。
6. 確認結果を取得した後、別操作で下書き保存する。保存結果を確認する。画像1枚成功を記事全体の完成と扱わない。

観測した配置は選択段落の後だった。画像前の説明文が正しいキャプション配置を意味するとは限らないため、画像直下のキャプション等は別途確認する。

## 失敗の切り分けと停止条件

| 観測 | 判断と対処 |
|---|---|
| 全選択後の貼り付けで本文・画像が増える | 選択成立を確認していない。追記を検出した時点で停止し、保存しない。Control/Meta等を盲目的に切り替えて再試行しない。 |
| フォーカスがBODY、選択が本文末尾 | 現在の選択状態の証拠。いつ外れたか、過去の全失敗の原因までは断定しない。 |
| 操作前に安全確認で拒否 | noteのアップロードエラーではない。拒否理由に従い停止、または許された読み取りで安全な前提を示す。迂回しない。 |
| アップロード後に本文ロケーターがタイムアウト | 再アップロードせず画面を読む。モーダルによって本文が操作対象から外れた可能性がある。 |
| 「複数画面で編集されています」 | 競合元を推測しない。現在／別画面の選択で他の変更を上書きし得るためユーザーに採用版を確認する。承認後に選択・保存し、本文と画像を再確認する。 |

新規下書きへの作り直しはユーザーが選んだときに行う。今回、空の本文への整形HTML挿入は成功したが、既存本文の全選択・置換の成功証拠にはならない。旧下書きの復旧も別タスクとして扱い、実施していなければ復旧済みと言わない。

## 完了条件

- 画像マーカーを実素材に対応づけ、素材挿入確認後に不要なマーカーを処理する。
- ハッシュタグは本文中の文字列とnoteのタグ設定を区別し、実際の設定・保存を確認する。公開は別の明示的指示が必要。
- 画像、実スクショ、キャプション、見出し、重複、タグ、保存状態を個別に報告する。
- セッション途中の観測結果を、別セッションの検証済み手順として一般化しない。現在の成果物を改めて確認する。
